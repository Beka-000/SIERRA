## 1. Общие сведения

### 1.1 Название системы
Sierra Coffee — веб-система управления кафе, объединяющая клиентскую часть для просмотра меню, оформления заказов и бронирования столиков с административной панелью для сотрудников кафе.

### 1.2 Основание для разработки
Основанием для разработки является необходимость создать единое цифровое пространство для основных процессов кафе и сократить количество ручных операций.

### 1.3 Цель разработки
Создать современную веб-систему Sierra Coffee, позволяющую клиенту ознакомиться с меню, оформить заказ или забронировать столик, а сотрудникам кафе — централизованно управлять заказами, меню, бронированиями, клиентами и статистикой.

### 1.4 Основные задачи
- сформировать удобный каталог блюд и категорий
- реализовать корзину и оформление заказа
- предоставить сотрудникам рабочее пространство
- автоматизировать уведомления
- создать безопасную авторизацию
- обеспечить адаптивную работу

## 2. Назначение системы и пользовательские сценарии

### 2.1 Назначение
Система предназначена для Sierra Coffee, которая принимает заказы в заведении, через сайт, самовывоз и доставку. Архитектура должна позволять в дальнейшем расширить проект до нескольких заведений.

### 2.2 Целевая аудитория
- посетители кафе
- клиенты самовывоза
- клиенты доставки
- клиенты, бронирующие столики
- администраторы
- кассиры и официанты
- сотрудники кухни
- менеджеры

### 2.3 Сценарий заказа клиента
1. Клиент открывает сайт.
2. Просматривает категории и блюда.
3. Добавляет позиции в корзину.
4. Выбирает самовывоз или доставку.
5. Указывает контакты.
6. Выбирает оплату.
7. Подтверждает заказ.
8. Получает номер заказа и уведомление.

### 2.4 Сценарий бронирования
1. Выбирает дату и время.
2. Указывает количество гостей.
3. Система проверяет доступность.
4. Вводит контакты.
5. Создаётся бронь.
6. Получает подтверждение и напоминание.

### 2.5 Сценарий обработки заказа
1. Новый заказ появляется у сотрудника.
2. Сотрудник подтверждает заказ.
3. Заказ передаётся на кухню.
4. Кухня меняет статус.
5. После готовности заказ передаётся на выдачу или доставку.
6. После завершения сохраняется в истории.

### 3.2 Клиент

просмотр новых заказов; подтверждение и изменение статусов; просмотр состава и комментариев; работа с бронированиями; просмотр доступности столиков.

### 3.4 Сотрудник кухни
просмотр заказов; состав блюд и модификаторов; изменение статусов приготовления; отметка готовности; фиксация проблем.

### 3.5 Менеджер
управление меню и категориями; акции и промокоды; столики; статистика; клиенты; заказы и бронирования.

### 3.6 Администратор

## 4. Функциональные требования: меню

### 4.1 Главная страница
информация о кафе и режиме работы; актуальные акции; популярные блюда; переход в меню; переход к заказу; переход к бронированию; контакты и адрес.

### 4.2 Каталог меню
Меню отображается с разделением на категории. Для блюда указываются категория, название, описание состава, цена, фотография, вес или объём, аллергены при необходимости, доступность и признак рекомендуемого блюда.

### 4.3 Управление меню
создание и редактирование категорий; изменение порядка; создание и редактирование блюд; скрытие без удаления; изменение цены и доступности; загрузка фотографии; удаление с учётом связанных заказов.

### 4.4 Поиск и фильтрация
поиск по названию; фильтрация по категории и доступности; сортировка по цене и популярности; сброс фильтров.

## 5. Функциональные требования: корзина и заказы

### 5.1 Корзина
добавление и удаление блюда; изменение количества; комментарий к позиции; модификаторы; автоматический пересчёт; промокод; итоговая стоимость.

### 5.2 Оформление заказа
имя; телефон; email при наличии; самовывоз или доставка; адрес доставки; желаемое время; комментарий; способ оплаты.

### 5.3 Статусы заказа
| Статус | Описание |
|---|---|
| `NEW` | создан |
| `CONFIRMED` | подтверждён |
| `COOKING` | готовится |
| `READY` | готов |
| `OUT_FOR_DELIVERY` | передан курьеру |
| `COMPLETED` | завершён |
| `CANCELLED` | отменён |

### 5.4 Данные заказа
Уникальный номер, дата и время, данные клиента, состав, итоговая сумма, способ получения, способ оплаты и история изменения статусов.

### 5.5 Панель заказов
Очередь заказов с фильтрацией по статусу, времени, типу получения и номеру.

### 5.6 Правила изменения
После передачи в приготовление изменение состава клиентом не допускается, если это запрещено настройками. Все изменения статуса фиксируются.

## 6. Бронирование столиков

### 6.1 Функционал
просмотр доступных дат; выбор времени; количество гостей; проверка доступности; контакты; создание, изменение и отмена; подтверждение сотрудником при необходимости.

### 6.2 Сущность бронирования
идентификатор; столик; имя; телефон; дата; время начала; продолжительность; количество гостей; комментарий; статус.

### 6.3 Статусы
| Статус | Описание |
|---|---|
| `PENDING` | ожидает подтверждения |
| `CONFIRMED` | подтверждено |
| `ARRIVED` | клиент пришёл |
| `COMPLETED` | завершено |
| `CANCELLED` | отменено |
| `NO_SHOW` | клиент не пришёл |

### 6.4 Управление столиками
Менеджер создаёт столики, задаёт номер, вместимость, зону и статус. Столик может быть временно недоступен.

### 6.5 Защита от двойного бронирования
Перед сохранением система повторно проверяет доступность. Пересекающиеся бронирования одного столика не допускаются.

## 9. Авторизация, API и интеграции

### 9.1 Авторизация
регистрация; вход; выход; восстановление пароля; хеширование; защищённые маршруты; проверка прав; защита админ-панели.

### 9.2 API
Backend предоставляет API для клиента и админ-панели. Группы: `auth`, `menu`, `orders`, `reservations`, `users`, `promocodes`, `notifications`, `analytics`, `files`.

### 9.3 Telegram
При подключении Telegram Bot система передаёт сотрудникам уведомления о новом заказе и критических проблемах.

### 9.4 Платежи
При наличии онлайн-оплаты используется внешний провайдер:

`клиент → заказ → провайдер → подтверждение → webhook → Backend → обновление статуса`

Предусматриваются создание платежа, статус, успех, отмена, webhook и защита от повторной обработки.

### 9.5 AI-функционал
рекомендации блюд; естественный поиск по меню; генерация описаний для менеджера; анализ отзывов; AI-помощник для анализа продаж.

## 10. Нефункциональные требования

### 10.1 Производительность
Типовые API-запросы — ориентировочно до 2 секунд при штатной нагрузке; не менее 100 одновременно работающих пользователей в первой версии; отсутствие потери заказа при повторной отправке; быстрая загрузка основных экранов.

### 10.2 Безопасность
HTTPS; хеширование паролей; защита от SQL-инъекций и XSS; CSRF там, где применима; валидация Frontend и Backend; RBAC; ограничение админ-API; секреты в environment variables; журналирование.

### 10.3 Надёжность
сохранность заказов; резервное копирование БД; целостность данных; обработка ошибок оплаты и недоступности внешних сервисов.

### 10.4 Интерфейс
адаптивный дизайн; мобильные устройства; понятная навигация; единая дизайн-система; состояния loading/error/empty; понятные ошибки; минимум действий для заказа.

## 11. Архитектура и база данных

### 11.1 Архитектура
Предполагаемая схема:

`Frontend → Next.js → API/Server Actions → Backend-логика → PostgreSQL`

Дополнительные сервисы подключаются через API: объектное хранилище, платёжный провайдер, Telegram Bot и AI API.

### 11.2 Технологический стек
| Компонент | Технология |
|---|---|
| Frontend | TypeScript, Next.js |
| Backend | серверная логика Next.js/API или выделенный backend |
| Database | PostgreSQL |
| ORM | Prisma или аналогичный инструмент |
| Authentication | JWT/session + защищённые cookies |
| Storage | S3-совместимое объектное хранилище |
| Deployment | Docker, HTTPS |

### 11.3 Основные сущности БД
Users, Roles, Profiles, MenuCategories, Products, ProductModifiers, Orders, OrderItems, Payments, Reservations, Tables, Promocodes, LoyaltyAccounts, Notifications, Files, Reviews, ActivityLogs

### 11.4 Связи
- один пользователь — много заказов
- один заказ — много позиций
- одна категория — много блюд
- один столик — много бронирований в разные интервалы
- один заказ — связанные события оплаты
- один пользователь — один бонусный счёт
